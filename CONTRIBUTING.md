# Contributing to VoocHealth

Thanks for taking the time to contribute. This repository is a Bun workspace with three apps: React Native/Expo (`apps/mobile`), Elysia on Cloudflare Workers (`apps/backend`), and a standalone HarmonyOS ArkTS watch app (`apps/watch`).

By participating you agree to keep discussion respectful and focused on the change at hand.

## Before you start

- Open an issue (or comment on an existing one) before starting a non-trivial change, so the approach can be agreed first.
- Report vulnerabilities privately — see [SECURITY.md](SECURITY.md). Never open a public issue for a security problem.
- Keep one pull request scoped to one problem. Unrelated refactors belong in a separate PR.

## Setup

Prerequisites: **Bun 1.4.4+**, **Node.js 18+**, and **Huawei DevEco Studio** only if you touch the watch app.

```bash
bun install        # install root and workspace dependencies
bun start          # start the Expo dev server for apps/mobile
bun backend:dev    # run the API locally
```

Do not run npm, pnpm, or yarn. Do not run Bun or Node tooling inside `apps/watch`; it is built exclusively with DevEco Studio / Hvigor.

## Repository rules

`AGENTS.md` documents the architecture boundaries. In short:

- `apps/mobile/src/features/<feature>/` holds feature code; files in `apps/mobile/app/` are thin route files.
- Install mobile packages with `bunx expo install <package>` so versions match the Expo SDK. Never hand-edit `ios/` or `android/`, which are generated by Expo CNG.
- `apps/watch/entry/src/main/ets/features/<feature>/` holds watch feature code; pages live in `ets/pages/` and are registered in `main_pages.json`.
- Backend schema changes go through Drizzle in `apps/backend/src/db/schema.ts` plus a generated migration.

## Branching and commits

Branch from `main` and use a descriptive name:

```text
feat/profile-keyboard-motion
fix/offline-auth-submit
chore/community-files
```

Write commits in the Conventional Commits style already used in the history, for example `fix(mobile): guard WeightChart against empty weights`. Keep commits small and coherent, and stage only files related to your change.

## Verification

Run the checks that match what you changed before opening a pull request.

```bash
bun run lint               # lint mobile and backend
bun run fmt:check          # formatting
bun run mobile:typecheck   # mobile typecheck
bun run mobile:test        # mobile unit tests
bun run backend:typecheck
bun run backend:test
bun run mobile:test:e2e    # Maestro flows, when your change affects them
```

For watch changes, verify the build and behaviour in DevEco Studio, and state the device or simulator used. In the PR description, list the commands you ran and anything you could not verify.

## Pull requests

- Fill in every section of the pull request template: summary, verification, risks, and checklist.
- Link the issue the PR resolves (`Closes #123`).
- Note breaking API changes, D1 migrations, new bindings or secrets, and rollback steps.
- Never commit secrets, personal health data, or real user records.
- CI must pass. Changes to `main` require review; do not merge your own PR without approval.
